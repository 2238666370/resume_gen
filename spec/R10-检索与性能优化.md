# R10 检索与性能优化

> 来源：`requirements.md` §4
> 阶段：贯穿各阶段 | 难度：⭐～⭐⭐⭐ | 依赖：视子项（O1 是 O2/O3/O4 的前置）

## 1. 定位

在功能需求之外补齐「数据检索」与「系统性能」。核心是：

1. **统一消息队列为 Redis Stream**（本轮重点），替代当前进程内 `InMemoryMessageQueue`，并以 `MessageQueue` 抽象隔离，为异步埋点、AI 异步、ES 同步、导出等场景提供持久化、可重试、可多实例的削峰解耦能力。
2. 简历/社区/模板搜索从 MySQL `LIKE` 升级为 Elasticsearch 全文检索（可选依赖，可降级）。
3. 补齐对象存储、多级缓存、公开接口限流、慢查询与前端构建等快赢项。

> 原则：所有外部依赖（Redis / ES / OSS / MQ）均「可开关 + 可降级」，无外部依赖时系统仍可完整运行（沿袭 `redis|none`、`mysql|json` 可选依赖风格）。

## 3. 优化子项

### O1 消息队列升级：Redis Stream（本轮重点）⭐⭐⭐

**现状**：`InMemoryMessageQueue` 每队列一个 `LinkedBlockingQueue`，消费失败被静默吞掉（无重试、无死信），进程重启丢消息，无法多实例共享。仅适用于单实例、可容忍丢失的场景。

**方案**：保留 `MessageQueue` 抽象不变（`publish` / `subscribe(queue, concurrency, handler)`），新增 `RedisStreamMessageQueue` 作为**默认实现**；`InMemoryMessageQueue` 降级为「无 Redis 环境 + 单测」兜底。后续如需更高吞吐、分区有序或重放语义，再实现 `KafkaMessageQueue` / `RabbitMQMessageQueue`（同抽象隔离，调用方零改动）。

- **Stream 建模**：队列名 `high`/`low` → Stream key `mq:stream:high` / `mq:stream:low`；死信 → `mq:stream:high:dlq`。
- **消费者组**：每队列一个消费者组（`mq:group:{queue}`，`XGROUP CREATE ... MKSTREAM` 幂等），`subscribe` 时按 `concurrency` 起多个消费者（`mq:consumer:{uuid}`），组内自动负载均衡。
- **消费语义**：`XREADGROUP GROUP ... COUNT n BLOCK ms STREAMS ... >` 拉取新消息；处理成功 `XACK`；处理失败**不 ACK**，消息滞留 PEL 由重试线程接管。
- **失败重试 + 死信**：后台线程定期 `XAUTOCLAIM`（`claim-idle-ms` 判卡死）接管超时未 ACK 的消息重投；单条消息重试次数超过 `retry.max` 后 `XACK` 并 `XADD` 到死信 Stream（可观测、可人工补偿）。
- **持久化**：Redis AOF/RDB 保证消息落盘，进程重启不丢；多实例共享同一 Stream，天然支持水平扩展。
- **降级**：`mq.type=memory` 时回退 `InMemoryMessageQueue`（无 Redis 可运行，行为等同现状）。

**受益方**：AI 异步任务（`AiAsyncService` 现有双队列无缝切换）、埋点异步（O2）、ES 异步同步（O4）、导出/聚合等耗时任务。

### O2 埋点异步化 ⭐⭐

**现状**：`StatService.track` 同步 `insert access_log` + `upsert stat_minute`，分享页/社区页高并发下阻塞主链路。

**方案**：埋点事件 → `MessageQueue.publish("low", json)`（复用 O1 Redis Stream）→ 消费者攒批（如 200 条或 2s 触发）批量 `insert access_log` + 幂等 `upsert stat_minute`。保留 `stats.async.enabled=true` 开关，`false` 时同步直写（对齐现状）。

### O3 AI 异步结果持久化 ⭐⭐

**现状**：`AiAsyncService` 任务状态/结果存 `ConcurrentHashMap`，进程重启后 `GET /api/ai/task/{taskId}` 返回 404。

**方案**：任务元数据（`taskId/taskType/userId/status/result/error`）持久化到 Redis Hash `ai:task:{taskId}`（TTL 1h，随 `mq.type` 生效）；`mq.type=memory` 时仍用内存表兜底。任务消息走 O1 Redis Stream，结果写 Redis，轮询/SSE 均从 Redis 读，进程重启后可继续查询。

### O4 全文检索（MySQL LIKE / Elasticsearch，yml 开关）⭐⭐⭐

> 状态：**已落地抽象 + 双实现**。`search.engine=mysql`（默认）走 LIKE；`search.engine=elasticsearch` 走 ES（IK 分词），ES 不可用时自动降级。

**抽象**：`SearchService`（`mysql`/`elasticsearch` 双实现，随 `search.engine` 切换），使用方（`ResumeService`/`CommunityService`）只依赖接口，不感知底层。
- `MysqlSearchService`（默认）：`active()=false`，检索返回 null → 调用方走 LIKE。
- `ElasticsearchSearchService`：REST 直连 ES（不引版本敏感客户端依赖），IK 分词建索引，命中返回 id 后回源 MySQL；调用异常返回 null 自动降级。

**已实现**：
- 用户端简历列表 `GET /api/resumes?keyword=`（标题匹配，强制 `user_id` 过滤）。
- 社区信息流 `GET /api/public/community/posts?keyword=`（`title/summary/tags`，仅 online）。
- 前端：`ResumeListPage`、`CommunityPage` 新增搜索框。
- 索引异步同步：新增 `SearchIndexSyncService`，简历保存/删除、社区发布/审核/删除时经 **O1 消息队列** 异步同步到 ES（最终一致）；ES 未启用时全部 no-op。
- 启动自动建索引（IK mapping），建索引失败仅告警不阻断启动。
- 社区帖补齐 `idx_resume(resume_id)` 索引。

**配置**：
```yaml
search:
  engine: mysql            # mysql | elasticsearch
  elasticsearch:
    url: http://localhost:9200
    index-prefix: resume_gen_
```

**验证（真实 ES 7.12.1 + IK）**：
- 启动自动建索引：`resume_gen_resume` / `resume_gen_post` 创建成功。
- 简历保存 → MQ 异步同步 → ES 文档写入成功（含 `userId/title/summary/skills/companies/positions/projects/schools`）。
- IK 全文检索命中：`架构`/`高并发`/`规则引擎`/`计算机`（中文分词）、`Redis`（技能）、`某某科技`（公司）均命中。
- 走 ES 而非 LIKE 的证据：MySQL `LIKE '%冒烟%'` 返回 2 条，ES 检索仅返回 1 条（只有被索引的简历命中）。
- 降级：`engine=elasticsearch` 且 ES 未启动时，应用正常启动并告警降级，检索经 MySQL 返回正确结果。

### O6 多级缓存与公开接口限流 ⭐

> 状态：**已落地**。

**现状**：仅 Redis 一级缓存；仅 AI 接口有频控。

**已实现**：
- 本地缓存：`TemplateService.listPublic()` 增加 60s TTL 本地缓存（零依赖实现），模板 CRUD/审核时失效，热点模板列表不再每次查库。
- 公开接口限流：新增 `PublicRateLimiter`（复用 `RateLimitStore` 抽象，Redis 全局 / 内存单机），接入 `GET /api/public/shares/*` 与 `GET /api/public/community/posts`，按 `ip:` 维度计数，超限 429；通过 `resume.public-rate-limit` 配置（`enabled/limit/window-seconds`）。

### O7 慢查询与索引优化 ⭐

> 状态：**已落地**。

**现状**：offset 深分页；R9 `listResumeStats` 逐简历子查询（N 个子查询）。

**已实现**：
- R9 简历统计由「每份简历 4 个子查询」改为 **派生表 `LEFT JOIN` 聚合**（`access_log` / `community_post` / `resume_share` 各按 `resume_id` group by 一次），查询数从 O(N) 降为固定 4 次，并对空数据 `COALESCE` 补齐 0。
- `community_post` 补 `idx_resume(resume_id)` 组合索引（已建）。
- 既有 `access_log(idx_resume_ts)`、`stat_minute(uk_time_metric_dim)`、`community_post(idx_status_time)` 索引覆盖统计与信息流热查询。

### O8 CDN 与前端构建优化 ⭐

> 状态：**已落地代码分割**。

**已实现**：
- 路由级懒加载：`App.tsx` 全部页面改用 `React.lazy` + `Suspense`，各页面独立 chunk。
- 大依赖分包：`vite.config.ts` 将 `html2canvas/jspdf/html2pdf.js` 拆为 `vendor-export` chunk（导出能力按需加载）。
- 效果：首屏主 chunk 由 ~690KB 降至 ~290KB（gzip 96KB），导出库 203KB 独立按需加载。
- 后续（CDN/图片懒加载）待部署环境确定后接入。

## 5. 验收标准

- **O1**：`mq.type=redis` 时消息经 Redis Stream 投递/消费，进程重启消息不丢；消费失败自动重试，超限进死信队列；多实例可共享消费。`mq.type=memory` 时行为等同现状。
- **O2**：埋点异步入队后主链路不阻塞，消费者批量落库，PV/UV 口径不变。
- **O3**：AI 任务重启后 `GET /api/ai/task/{taskId}` 仍可查询。
- **O4**：`search.engine=elasticsearch` 时简历/社区/模板搜索支持分词与相关性排序，ES 挂掉可降级 `LIKE`。
- **O5**：头像/封面/缩略图可上传并返回可访问 URL；`type=none` 维持 URL 填写。
- **O6**：公开接口与 AI 接口限流生效，热点数据命中多级缓存。
- **O7**：深分页、简历统计等慢查询耗时下降。

## 6. 难点与风险

- **Redis Stream 消费语义**：消费者组 + ACK + PEL 的重试/死信编排需正确处理 `XAUTOCLAIM` 卡死消息与消费者崩溃后的消息重分配，避免消息重复消费（处理需幂等）。
- **消息幂等**：Redis Stream 是 at-least-once，异步埋点/AI/ES 同步的消费者处理必须幂等（如 `stat_minute` upsert、ES 按 `id` 覆盖写）。
- **ES 一致性**：最终一致 + 死信补偿；ES 数据隔离（`user_id` 过滤）。
- **OSS 权限与成本**：签名直传的签名时效与访问控制、桶成本。
- **多实例运维**：`mq.type=redis` 需共享 Redis，`consumer-prefix` 需实例唯一；Kafka/RabbitMQ 后续仅在吞吐/重放诉求明确时切换（同 `MessageQueue` 抽象）。
